# Analytics Corrections Report — Root Cause, Code Diffs & Verification

## 1. Summary of Verified Defects & Engineering Corrections

| # | Phase | File(s) Modified | Root Cause Identified in Audit | Exact Engineering Correction Applied | Verification Test |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | Phase 1 | `analytics.snapshot.ts`, `analytics.repository.ts` | Dual persistence (PostgreSQL + `.data/store-state.json`) could feed duplicate transactions or products if merged without canonical deduplication. | Implemented `deduplicateTransactions` (by `id` and `idempotencyKey`, preferring `syncStatus === 'synced'`), `deduplicateProducts`, `deduplicateReturns`, `deduplicateStockMovements`, and `deduplicateCustomers`, plus `sourceOfTruthMatrix`. | `Phase 1` test in `src/analytics/analytics.test.ts` |
| **2** | Phase 2 | `sales.metrics.ts`, `financial.metrics.ts` | `computeLineItemCostInCurrency` previously used current `product.costPrice` for all historical sales and fell back to `item.total * 0.45` when a product was missing. | Replaced with `resolveHistoricalLineItemCost` implementing a strict 4-tier hierarchy (`exact_frozen_at_sale` -> `reconstructed_from_price_history` -> `estimated_from_current_catalog_cost` -> `incomplete_missing_cost`). Removed `0.45` fabrication completely. | `Phase 2` test in `src/analytics/analytics.test.ts` |
| **3** | Phase 3 | `sales.metrics.ts`, `customer-branch.metrics.ts` | Voided invoices and merchandise returns were lumped together; partial returns in `returns` / `return_items` were not deducted from Net Sales, Tax, or COGS; tax-inclusive invoices were not distinguished from tax-exclusive invoices. | Added `isTransactionTaxInclusive` detection and `resolveReturnsForTransaction`. Voided invoices are excluded from sales (`voidedSalesExcluded`), while merchandise returns (`returnsAmount`) reduce Net Sales, Tax Collected, and COGS (capped at original invoice value). | `Phase 3` test in `src/analytics/analytics.test.ts` |
| **4** | Phase 4 | `financial.metrics.ts` | `netOperatingProfit` was computed as `grossProfit - shrinkage` even when operating expenses were missing, and `breakEvenSalesRevenue` divided inventory restock purchases by gross margin ratio. | Exposed `profitAfterRecordedShrinkage` explicitly; set `netOperatingProfit: null` (`unavailable_missing_operating_expenses`) and `breakEvenSalesRevenue: null` (`unavailable_missing_fixed_costs`) unless `fixedOperatingExpensesOverride` is supplied. Deducted `cashRefundsForReturns` from `totalCashInflows`. | `Phase 4` test in `src/analytics/analytics.test.ts` |
| **5** | Phase 5 | `inventory.metrics.ts` | `stockTurnoverRatio` divided unit sales by `currentStock + 0.5 * unitsSold` while `overallStockTurnoverRatio` divided `totalCogs` by ending `totalInventoryValueAtCost`. Pending inbound purchase orders were ignored in reorder quantities. | Reconstructed `reconstructedBeginningStock` from period movements to compute `averageInventoryValueAtCost = ((Beginning + Ending)/2) * unitCost` and `costBasedStockTurnoverRatio = COGS / AverageInventoryValueAtCost`, while labeling unit velocity as `estimatedUnitSellThroughRatio`. Subtracted `pendingInboundPurchaseUnits` from reorder recommendations. | `Phase 5` test in `src/analytics/analytics.test.ts` |
| **6** | Phase 6 | `forecasting.engine.ts` | Backtesting used a single static tail split (`testLen <= 7`) regardless of whether the user requested a 7, 30, or 90-day horizon, lacked a `naive_last_value` baseline, and labeled short-history bands as calibrated confidence intervals. | Implemented multi-origin rolling backtesting (`selectedOrigins` up to 5 origins), added `naive_last_value`, computed `forecastBias`, `biasPercent`, `empiricalCoverage80Percent`, `empiricalCoverage95Percent`, penalized aggressive trend extrapolation on short histories for 30/90d horizons, and labeled short-history bands `Estimated Uncertainty Ranges (80% / 95%)`. | `Phase 6` test in `src/analytics/analytics.test.ts` |
| **7** | Phase 7 | `analytics.permissions.ts`, `analytics.routes.ts`, `BusinessIntelligenceDashboard.tsx` | Client-supplied `x-user-role` header was trusted without checking `dataset.users`, `/api/analytics/financial` returned HTTP 200 with zeroed fields for cashiers, and unauthorized financial/cost metrics were masked as `0` (indistinguishable from zero profit). | Verified `userId` against `dataset.users` (`roleVerifiedFromServerStore`), enforced HTTP `403 Forbidden` on `GET /api/analytics/financial` for unauthorized roles, and masked restricted financial/cost fields as `null` (`Restricted / N/A` in UI). | `Phase 7` test in `src/analytics/analytics.test.ts` |
